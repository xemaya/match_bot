# P54 群记忆：成员公开备注与后台整理

状态：完成（2026-10-23，验收口径经用户调整，见文末）。D1–D3 按推荐执行。负责人 claude。依赖：P53（主 agent 与 `groupView`）。范围 `packages/db`（新表与迁移）、`packages/agent`（整理员 agent、`groupView.memberNotes`）、`packages/queue` 与 `apps/worker`（后台整理任务、保留期 cron）、`packages/eval`。

总体路线见 [P52](./P52-researcher-subagent-single-voice.md#总体路线p52p55)。

## 为什么

P53 的群视图只覆盖最近 6 小时、20 行。群里真正有用的"谁有什么、谁住哪片、谁上周问过什么"往往在更早：第七轮里阿明在群里说过有空房，几天后小鱼找房时 A2H 只会去 A2H 市场搜；A2H 一周内给同一成员推荐同一个博物馆三次（0.35.0 用 `recentReplies` 补了后者，但只限 A2H 对这个人说过的话）。

现状核对（2026-10-22）：triage 的 `peer_offer` 在 `inbound.ts` 里以 `peer_offer_noted` 丢弃，并没有记下来；`supplies` 表 0 行。也就是说，群友公开的供给从来没进过任何记忆。

业界参照：OpenClaw 把长期记忆（MEMORY.md）只放在私聊主 session、群里不加载；Hermes 子 agent 不能写记忆；Letta 由后台 sleep-time agent 整理记忆，对话 agent 不改记忆，因此不增加对话时延。本包取后两条：**记忆只由一个后台整理员写，主 agent 只读**；并且只从**群里公开说过的话**整理，不从私聊整理。

## 设计

1. **新表 `member_notes`**（`MemberNote`）：`id`、`groupId`、`userId`（库内 id）、`kind`（`offer` 供给 / `need` 需求 / `context` 公开的处境，如"在 Mile End 住"/ `resolved` 已解决）、`text`（≤ 120 字，第三人称客观句，别名不入库）、`sourceMessageId`（必须是本群一条公开消息）、`createdAt`、`expiresAt`（= 来源消息 `receivedAt` + 30 天，与 `messages.text` 保留期一致）、`supersededById`。
2. **整理员（后台，不在热路径）。** 新队列任务 `memory_consolidate`，按群去抖：一个群有新消息后 10 分钟内最多跑一次。输入：该群上次整理之后的公开消息（别名）+ 该群现有未过期备注；输出（结构化工具调用）：新增 / 作废 / 标记已解决。模型用便宜档（`MEMORY_MODEL`，缺省同 `DEEPSEEK_MODEL`），`temperature 0`。代码门：每条备注必须能在来源消息里找到依据（复用 `unsupportedFeature` 式的子串 / 实体核对）；去掉电话、邮箱、门牌号、@handle、精确邮编（只留邮编区，如 E14）。
3. **读取。** 主 agent 的 `groupView.memberNotes`：当前提问者的备注 + 与当前任务主题相关的其他成员备注（代码按任务关键词 / 类别挑），≤ 8 条、≤ 1200 字，以别名呈现。`refer_member`（P53）的门放宽为"别名出现在 conversation、peerOffers 或 memberNotes 里"。
4. **peer_offer 不再只是丢弃。** triage 判 `peer_offer` 的消息仍不进 agent，但会触发该群的 `memory_consolidate`。
5. **保留与删除路径（§6 要求写明）。** `expiresAt` 到期由现有 cron 删除（不是置空，整行删）；来源消息被 30 天 cron 置空时，同步删除引用它的备注；群停用时删除该群全部备注；成员私聊 A2H"忘掉我" / `/forget` 删除其在所有群的备注（D3）。日志与 trace 只记备注 id 与 kind，不记 text（pino redact 加 `note.text`）。

## 决定（2026-10-22 按推荐执行）

- **D1 是否引入 `member_notes`。** 这是 AGENTS.md §6 意义上的新增个人数据字段：内容只来自群内公开发言、30 天到期、整行删除。推荐引入。
- **D2 整理的触发方式。** 推荐按群 10 分钟去抖；备选：每日一次（成本更低，但当天的供给当天用不上）。
- **D3 成员自助删除。** 推荐提供私聊 `/forget`；备选：只靠 30 天到期。

## 验收标准

1. 备注忠实度：抽查 40 条，≥ 95% 能在来源消息里找到依据；0 条含电话、邮箱、门牌号、@handle 或完整邮编。
2. 有用：`moments/r7` 上加入 `memberNotes` 后点名正确率不降、动作一致率 ≥ P53 结果；至少能复现一个 6 小时窗口外的正确点名（例如第七轮阿明的空房 → 小鱼的找房）。
3. 不拖慢对话：主 agent 热路径不新增模型调用；`groupView` 构建新增查询 p95 ≤ 50 ms。
4. 删除路径全部有测试：到期、来源置空、群停用、`/forget`。
5. `pnpm check` 全绿（db 基线除外）。

## 额度

整理员按群去抖，第七轮规模（约 350 条群消息 / 8 章）估计 40–60 次调用、每次 3–5k token，合计 ≤ 30 万；T6 离线回放同量级。开跑前报数。

## 实现记录（2026-10-22）

- 迁移 `20261023041204_member_notes`：枚举 `MemberNoteKind`、表 `member_notes`（外键对 groups / users / messages 均 `ON DELETE CASCADE`）、`groups.memory_consolidated_at`。`supersededById` 简化为 `supersededAt`。
- **触发改为 cron，不新开队列**：`consolidate_member_notes` 每 10 分钟一次，`groups.pendingMemory` 找出"上次整理后有新消息"的活跃群，每次最多 5 个群；效果与"按群 10 分钟去抖"相同（D2），少一条队列与载荷 schema。
- 整理员 `stages/notetaker.ts`：只给模型别名与行号；代码门——来源行必须是同一成员在本群的公开消息（仓储层再校验一次）、备注与来源行必须有词重叠、命中电话 / 邮箱 / @handle / 完整邮编 / 门牌号即丢弃。trace 只记条数，不记备注文字。
- 删除路径：`delete_member_notes` cron（到期、来源消息已被 30 天 cron 置空）；`groups.setPolicy(isActive=false)` 联删；私聊 `/forget`（在代码门之前处理，删除该成员在所有群的备注，只写 trace，不回消息——发确认需要新的出站形态，留作后续）。
- 主 agent 的 `groupView.memberNotes`：提问者自己的备注优先，再取与当前话题有词重叠的其他成员备注，≤8 条、≤1200 字，数据包里只有别名；`refer_member` 可以点名只在备注里出现的成员。

## 补充（2026-10-23，0.37.3–0.37.4）

- 代码按原句措辞纠正 kind（问句且无提供说法 → need；送出 / 自取 / 免费等 → offer），依据门槛 0.6，备注不得比原句长 6 字以上。三次各抽 40 条：忠实 36 / 35 / 34（**约 87.5%**），可保留 34 / 33 / 32；换 `MEMORY_MODEL=deepseek-v4-pro-0813` 后忠实 36 / 37 / 32，可保留 36 / 37 / 38——强模型主要减少了涉第三方的备注，忠实度没有明显提升，默认仍用 flash（整理员可随时改用强模型）。剩下的不忠实主要是轻度上下文补全与判官对"提到房东 / 某成员"的严格判定。
- **6 小时窗口外的点名复现**：`humanness:probe` 里一名成员 9 小时前说"那间房月底空出来了"（已超出群记录窗口，只在备注里），另一成员问 Mile End 空房，主 agent 两次都点名了提供者（"你不是说 Mile End 合租那间月底空出来嘛 这位正好月底要搬 要不要聊聊"）。

## 备注改为原话摘录（2026-10-23，0.37.5）

- 备注文本不再由模型改写：模型只挑哪一行、给出 kind，存的是该行原话（去 @、电话 / 邮箱 / 完整邮编 / 门牌号替换为 …，保留"31号"这类日期，≤120 字）。原话之外的内容从结构上进不了备注。
- kind 由措辞决定（求购 / 想要 → need，提供 / 送 / 转 / 我这还有 → offer，"定好了 / 搞定了" → resolved，其余问句 → need；模型给 offer 或 resolved 但原句没有对应措辞时降为 context）。
- 判官抽查（每次 40 条，判"只说原句说过的、kind 正确"）：run 7 窗口 34 / 34 / 37，留出的 run 6 窗口 13 / 13 / 13（共 15 条）——**约 87–89%，仍未到 95%**。剩下的分歧几乎都是 kind（如邀约算 need 还是 offer、条件性打算算不算 resolved），同一批数据两次抽样相差 ±3/40，判官本身的一致性已是上限的一部分。

## 验收口径调整（2026-10-23，用户决定）

用户同意把验收 1（忠实度 ≥95%）改为：备注文字 **100% 来自原话**（结构保证）、联系方式 **0**、kind 一致率 **≥85%**。注意选项标题写的是"忠实度 90% 记为达标"，而实测判官忠实度为 run 7 窗口 34 / 34 / 37（共 40，均值 87.5%）、留出的 run 6 窗口 13 / 13 / 13（共 15，86.7%）：**高于说明中的 85% 门槛、低于标题中的 90%**。按选项说明的 85% 口径记为达标；若以 90% 为准则仍差约 2.5 个百分点。
