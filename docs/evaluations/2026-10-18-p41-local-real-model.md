## 环境与范围

- 真实 worker 入站、任务规划/研究/交付、Postgres、DeepSeek 搜索、A2H 公开市场查询、strict JEV 和出站账本。
- 三个新建合成私聊用户，各两轮固定输入；发送端仅生成本地回执，没有 Telegram API 调用。不覆盖 Telegram 网络、群聊、队列消费或审批恢复。
- 专用 loopback 数据库 `matchbot_p41_live`，应用主干已有 15 项迁移。凭据只放私有临时环境文件。
- 本轮生成观察预算 300000 token，逐调用保守预留，单次输出最多 2400 token。搜索/JEV 不计入该预算；这不是服务端账单硬限制。
- 新脚本：`scripts/poc/p41-local-live/run.mts`。原始合成对话、工具调用和 traces 保留在忽略的 `logs/p41/local-1792337934415/report.json`，未提交原始日志或凭据。

## 判断

1. **新增条件后的补查行为在本次三个追问中都出现了**，打印机没有重现 P39 的零新查询行为。但当前只是实测路径，不能据此证明一定由 P41 兜底分支触发；自然模型行为也会补查。
2. **GP 仍是部分交付。** 第二轮从首轮 Roserton Street Surgery 转到 Island Health，未维持同一候选核验完整线上入口。新增查询并不等于解决用户目标；这是后续候选连续性与定向检索要处理的问题。
3. **无线打印机仍缺证据。** 新搜索有效执行，最终承认无法确认，没有冒充条件已满足；重复 `market_enrich` 被去重保护拒绝。应把“补查完成”和“找到满足条件的商品”分开评价。
4. **看展第一轮发现收尾恢复不足。** `outbound_input` 留痕 `invalid_evidence / unsupported numerical values time:17:45`，之后没有新的生成调用修订答案，而直接进入 `request_status:no_answer`。目前确认的是校验拒绝后没有恢复有用交付；尚未独立核对原始网页来判断这个时间值究竟是模型新增、来源裁剪还是校验识别问题，不能直接认定为幻觉。
5. **看展第二轮受测试预算干扰，不作为正常完成质量结论。** 固定追问含“这个展”，但第一轮实际只发出失败状态，未向用户展示展名。该输入仍验证了任务续接和新条件检索，不能视为自然用户对已交付展览的反馈。
6. 三个新用户只创建各自任务，各自第二轮均继续原任务；本轮未观察到跨用户串任务。这不是并发/session 隔离的完整证明。

本轮没有和旧版本做相同实时来源、相同会话的配对 A/B；不能把用量与 P39 的差值当成确定性性能提升。没有改动或放宽生产事实校验/JEV 门。结论是：本地真实链路可运行，补查路径得到验证，但功能完备性尚未通过，尤其是交付拒绝后的恢复与 GP 任务闭环。
